Digest of two weeks of measured performance work (2026-11-12 .. 2026-11-23, 31 rounds of a local work log). Nothing here was re-measured when this file was written. Structures the rows refer to: [GPU.md](GPU.md), [GRAPHICS_PIPELINE.md](GRAPHICS_PIPELINE.md), [MEMORY.md](MEMORY.md). Ideas not yet tried: [RESEARCH.md](RESEARCH.md).

## How to add an entry

```
date | change (+ commit id) | files | hypothesis (one sentence) | measurement (build, mode, resolution, window, runs, in-run A/B or separate, store cold/warm)
result (before -> after, unit; say "inside noise" when it is) | status (in main | dropped | probe only | not pushed | measurement only; + the switch that undoes it)
Add the row at the bottom of "Optimization log". Failures and neutral results get a row too. Older rows fold files into "change" and have no hypothesis column.
Measured numbers keep their conditions: a number without date, build, mode, resolution and window is not entered.
fps = window-title frame counter unless "ms/frame" is written; a change under ~1 ms is judged only by an in-run alternating switch.
```

Conventions
- Hardware for every number: RTX 3050 Laptop GPU, Ryzen 5 3600, 31.9 GB RAM, Windows 11, NVIDIA driver (version not stated in the notes). One PC, one game at a time.
- **Title A** = the first title studied (rounds up to 2026-11-15). **Title B** = the title the later rounds use. A third title ("title C") was tried once. Note: the fork's *commit bodies* use the opposite labels (there "title A" is the later title); this file follows the lead's labelling.
- **Scene A** = title A's first gameplay scene after loading, no input. **Scene B** = title B's first gameplay scene, character standing, no input (a few runs also used a later, heavier scene of title B, marked "scene B2"). Title B modes: *performance mode* (game cap 60, or 30 for the flip-rate it asks for) and *quality mode with ray tracing* ("quality+RT").
- "720p" / "1440p" / "4K out" = guest render size and, where stated, video-out size. The title's own 1440p/4K sizes were forced to 720p/1080p with local data patches (patch files hold game bytes and are not in the repository).
- Commit ids are the ones in this repository (`git log`). The work log quotes other ids for the same changes (history was rewritten); where a row cites a commit it is the repository id, "n/a" = not found by subject.
- "in-run A/B" = one process, a switch toggled every N seconds, paired windows compared. "separate runs" = two processes. Runs are single unless a count is given. fps are from the window-title frame counter (or overlay) unless "ms/frame" is given.
- A program id P1..P12 is a short anonymous stand-in for a shader hash; the same id is used throughout this file:
  P1 compute copy kernel ("dst[i]=src[i]", early-compute producer, scene A); P2 pixel shader that consumed P1's output; P3 compute fill kernel (scene A); P4 compute BVH bottom-up refit (title B); P5/P6/P7/P8 ray-traversal compute programs of title B (P5 = the big one); P9 compute program storing through a buffer descriptor read from a table at run time (title B); P10 compute program that built a garbage descriptor at main-mode load; P11 compute program that writes the thread-count/args words of other programs; P12 consumer program whose walk waited on P11's output.

## Measurement method used so far

**Scenes and run length**
- Scene A: reached by a script that presses buttons until a loading screen is seen, then skips cutscenes, then waits for an on-screen hint. Two screenshots (default 10 s and 30 s after the hint; 15/45 s in the first analysis) with the window title (frame counter, fps) and the in-game overlay. Later: frames between two screenshots 60 s apart ("window"), 120 s windows, 30 s windows. In-run alternating windows of 1.5 s to 20 s for changes under 1 ms.
- Scene B: scripted pad presses (cross at ~100/108/116 s, shoulder at ~150/165 s, cross at ~195 s), the game loads ~45 s, scene from ~240 s. Standard window for fps: frames between the screenshots at ~240-281 s and ~401-441 s (160 s), one run per build/arm, sometimes two.
- Run length 400-700 s per run; Nsight-style captures were 500 ms.
- The script stops a run on "no frame counter change for 120 s" (HUNG), refuses to start below a free-RAM threshold (6-10 GB; the title takes ~9 GB, emulator RAM 4.2-4.5 GB at menus, commit 19-30 GB of 32.7 during loads), and compares a listing of the game dump before/after (a game wrote into its own install folder once; since then the guest file system is read-only under the application folder).

**What is read**
- Window title fps (frame counter between two screenshots); in-game overlay (fps, ms/frame, worst frame, draws/frame, "CPU waiting on GPU" ms/s and waits/s, texture/buffer transfers MB/s, GPU memory, emulator RAM, compute programs compiled).
- `nvidia-smi` sampled each second (GPU utilization, clock, power; e.g. 99% / 57 W when the GPU is the limit); per-thread CPU time of the emulator process every 10 s (Get/QueryThreadTimes, psutil); non-invasive debugger stack samples of the busiest threads ("profiler": 25-320 samples, inclusive counts, call chains); a 1 kHz sampling profiler with its own unwinder for the GPU thread.
- Temporary in-tree probes, removed before each commit and kept as local diffs: per-function GPU-thread timers (ms/frame, outermost scope), GPU timestamp pairs per batch / render pass / dispatch / copy / upload (per-program ms/frame), wait probe with stacks and producer attribution, fault probe (guest faults per block, time in handler), frame probe (zones per thread, flip/vblank pacing, wait anatomy), event ring of buffer transfers dumped when fps collapses, and in-run A/B switches (a thread flips an atomic every N s and prints per-phase fps).
- Vulkan/driver tools: NV device-diagnostic checkpoints (marker = program id) and VK_EXT_device_fault (later the option `--gpu-crash-diagnostics`); Windows TDR events (nvlddmkm event 153) confirm a hang; `spirv-val` on every module; `spirv-cross` on the emulator's own SPIR-V dump to understand what a compute program does (a fill, a copy).
- Nsight Graphics GPU Trace (2026.4, CLI, 500 ms capture, real-time shader profiler, Ampere metric set) analysed through its MCP server; it needed the GPU performance counters unlocked for all users, no `--platform` option, and could not attach to the emulator in an earlier try (the injected server never listened; a firewall prompt was suspected, not confirmed). The one successful capture was of title B quality+RT at 1080p (7 frames, ~83 ms each under the profiler).

**A/B discipline (as it evolved)**
- Early: separate runs, "before / after" 60 s windows.
- 2026-11-14: separate runs differ by +-1.5 fps (two runs of one build: 39.9 / 43.9), so a change under ~1 ms is judged only by an in-run alternating switch (A B A B ... A, each B against the mean of its neighbours, medians of 5-14 pairs).
- 2026-11-16: at 720p the run-to-run spread is ~2 fps with dips to 41-44 inside runs; the same build gave 49.6-57.9 fps over one day on scene A (GPU at 85-87 C).
- 2026-11-17: pitfall: shots every 40 s with an A/B period of 20 s always land in the same phase.
- 2026-11-19..23 (scene B quality+RT): 160 s windows, two arms interleaved or two runs each, shader store cleared per run (cold) for every A/B; the first run after a build is "cold", a second run on the same exe is "warm" (see noise).
- A picture check (screenshot of the same scene, same instant) accompanies every kept change. Ceiling probes (stale reads, skipped waits, skipped uploads) are explicitly marked "picture wrong, measurement only".
- Rule adopted by the lead during the work: ceilings that need inexact data are not committed; exact fast paths only.

**Known noise sources**
- Driver device loss (TDR): see "Regressions and open defects". About 1 in 4 runs lost the device at main-mode load (~215 s) during 2026-11-19; ~1 in 10-20 runs end in the P4 runaway (16 -> 3 fps) later.
- Cold pipeline/shader store: the store is keyed by the build time, so the first run of each build loads slowly (pipeline compile peak 6.6-8.3 s; driver pipeline-cache misses after shader changes). Until 2026-11-21 runs on a warm store drew some programs with a wrong pipeline layout (fixed), so warm runs measured ~12% low and native-RT warm runs 4-5 fps.
- Memory pressure: a device loss when another process's job took ~16 GB commit; 3 device losses in 20 two-queue runs all happened within one hour when disk and RAM were short.
- "Slowdown" runs: a base run of the same build sometimes ran at 16.65 vs 18.78 fps (160 s window) with no cause found; scene A is faster early in a run (54.1 fps at 108-128 s vs 50-51 fps after 180 s on equal builds). A 60 Hz virtual-vblank clock quantizes flips: frames that miss a tick wait for the next (worst frame exactly 3 ticks = 50 ms).
- Frame-rate overlay layer (RTSS) crashes Vulkan device creation (empty log, exit 0xC0000005); runs set `DISABLE_RTSS_LAYER=1`.
- Probe overhead (a probe build runs a few percent slower than the clean build; the log says so where it was priced).

**Switches used for unlocking frame rate**
- `--vblank-frequency N` (upstream option; 120/180/360 used so flips are not quantized to 60 Hz; at >=119 Hz the emulator reports a 120 Hz mode to the game).
- `--ignore-flip-rate` (fork, commit 05ed14216): flip at every vblank even if the title called `sceVideoOutSetFlipRate(1)` (quality mode does: 30 fps cap; menus 30 -> 60 fps with it). Performance mode asks for rate 0.
- `--present-mode Immediate`, window size options.
- Holding one title's own frame-interval setting at the 60 fps value: in performance mode no gain above 30 (the cap was not the pacing); combined with the 1080p patch in quality+RT it was slower, 10.1 fps vs 14.8 (guest CPU read-back waits 4 -> 50 ms/frame): not usable there.
- Data patches with `"hold": true` (fork, 9b1b55a55): re-write a game value whenever the game writes its own; used for render size and video-out size (see rows of 2026-11-16). Patch offsets written for another loader's base convention landed every held write at the wrong address until converted.

## Known remaining waits and costs

1. **Chain of GPU-written values the GPU thread reads on the CPU** (quality+RT; mechanism): the descriptor walker, thread-dimension indirect args and condition words depend on values a previous GPU program wrote this frame, so the GPU thread blocks on a download and the whole RT pass sits on the critical path. Tried: speculation (stale reads, wrong), byte-exact reads (true dependencies remain), early compute (works for P1 in title A), both-arms evaluation of condition-only loads, GPU derivation of thread counts (`8ebe9a09`), CP-known value overlay (`b386cf25`), scalar reads through the cache buffer (`b386cf25`), run-time descriptor learning (disabled), GPU-SRT masks (slower), table fast path (crashes, RT slower). Every removed link moved the wait to the next reader. Left (2026-11-23): one wait per frame (~11-14 ms) for P12's written-buffer descriptor from a 0x140-byte table P11 writes, and WRITE_DATA faults over pages with pending GPU writes. Needs GPU stores through run-time descriptors with write tracking, or a CPU-known candidate set.
2. **GPU-thread CPU bookkeeping**: `NtProtectVirtualMemory` for page watchers (11-19% of busy time; sticky pages would cut it but corrupt data), ObtainBuffer/FindBuffers (20-25% inclusive), eager read-back record/complete (~12-28% inclusive), BDA sync (~10%), RangeSet (~5%). Tried: parallel hashing (no fps), memos (partial), batched re-arm, in-place hashing, recorder thread, cuts a-j. While a wait remains on the critical path CPU cuts do not show in fps (2026-11-23).
3. **Run-time table marking** (quality+RT): ~10k ObtainBuffer calls per dispatch before the span fix; still 21k -> 12.7k per frame with the (dropped) fast path; the inexact ceiling is 18 -> 27 fps. Marking only spans that already have a cache buffer made it slower. A correct "mark only what the shader writes" needs GPU-side write tracking of run-time records: not done.
4. **Software-ray-tracing cost on the GPU**: P5 ~11-14 ms of ~35-48 ms; instruction-cache pressure (modules far above the instruction cache), lane-pair emission (~9 ms of P5's 16 in a timing probe), alpha-test code per candidate (~7.5 ms), `get_bda_pointer` ~9% of all GPU samples. ## Dead ends

Do not retry without new evidence.
- **Full GPU-side SRT (buffers, images, samplers) by mask/hash map** in this architecture: every partial mask slower; mask 31 85 ms GPU/frame vs 14; the cost is per-invocation loads and per-handle lookups, not bookkeeping. The mirror design (host view over PCIe) costs ~7% by itself. (Rows 2026-11-13/14.) another fork saw the same (3-6x GPU regressions; 20x for one shader with a range search).
- **Speculation / stale reads of GPU-written descriptors**: words change between frames; stale programs break specialization reuse (24 fps); stale ceilings crash or hang the title at load.
- **Reading the SRT on the GPU "to remove waits" in title A**: removing 82% of the walker faults changed fps by 0.
- **Merging submissions or flushing more/less often**: -1.6 ms / +0.05..0.39 ms.
- **Parallel page hashing as a fps lever** (3 tries; ms gain only), **ObtainBuffer read-range memo**, **pipeline-bind skip**: no gain.
- **Table fast path for run-time table marking, over-marking only cached spans, learned written pages**: wrong data or slower with RT.
- **Wide read-back on CPU fault** (whole GPU-written run): 2.3 fps.
- **Rewritten-page ("sticky") tracking on by default**: it makes the GPU read stale CPU data at main-mode load (bad descriptors, loop-guard trips, 7 of 27 runs).
- **Forcing no barriers around dispatches**: 14.8 -> 6.2 fps.
- **`get_bda_pointer` / `bvh_intersect` as real calls**, **per-invocation page memo**, **pair dedup**, **predicated-exec per-lane branches**, **opaque geometry replay split**: no gain or worse.
- **Splitting wave64 into independent halves for RT programs** (they use ballots and lane moves).
- **Static data patches for resolution of title B** (immediates, tables, reported display size): none changes the render size; only values the game computes at run time work (held values).
- **Reporting a 1080p display** to the game (no effect; the game was already given that), **`--report-window-resolution`**: dropped.
- **Native ray queries for speed** (+3% only).
- **Moving title A's compute fills/copies to the GPU as shaders** was replaced by clears/copies: do not undo.
- **Linear-image read-back default**, **stream buffer in cached host memory**: -14% / 0.
- **Suspending guest threads to find the bottleneck** (a sampler that suspends the busiest 5 stalls the game to 1 fps): use per-thread CPU times and wait states.
- **A "sync image->buffer for written texel buffers" fix for the dim sign**: not the cause, costs fps.

## Regressions and open defects

- **Device loss / GPU hang (TDR).** (a) Title A, host view / GPU-SRT masks: hangs in several masks (BDA reads of unbacked pages return 0 or stale, driving loops); `KYTY_GPU_SRT_LEARN=1` lost the device within two minutes in 3 of 3 runs (also with the submit worker off). (b) Early compute: 3 of 20 two-queue runs (all in one hour, RAM and disk short), 0 of 20 one-queue runs; unexplained. (c) Title B quality mode at main-mode load (~215 s): about 1 in 4 runs lost the device around 2026-11-19 (native RT 3/3, software 1/7). Caught with NV checkpoints and device-fault records: P4 (bottom-up BVH refit, whose last-arriving child walks the parent chain) loops forever on stale/garbage links. Guards: per-invocation loop guard (cost <=3%), clamp of GPU-read indirect dispatch counts, args read through the buffer cache. A residual runaway of P4 (16 -> 3 fps, permanent) happens in about 1 of 10-20 runs; the buffers' counters (parent<<3 | pending children) are corrupted wholesale on the GPU (counts 5/6/7 appear: a node decremented more than its children); candidates ruled out by probes: uploads over tracked GPU bytes (0), guest queue ordering, early compute off, native RT off, eager publication race (fixed, `fead0d20f`, rate dropped from ~4/10 to ~2/34 in the probe builds), sticky pages (fixed, off). Still open: GPU-side ordering of buffer joins/copies vs refit dispatches, atomics ordering, maximal reconvergence (tested in an interleaved batch, results not in the notes). A 2026-11-14 another fork code review of "instruction pointer invalid" device losses (different code base, not this fork) ranks fast-linked graphics-pipeline libraries on this driver as most likely; unconfirmed.
- **Loading-screen hang** (title A, ~1 in 5 loads): root cause = the fork's submit worker (out-of-order timeline signal); fixed in `080ffc3d2`; the lead's earlier candidate fix was a no-op.
- **Warm shader store drew wrong layouts** (-12%, native RT 4.5 fps): fixed `1766a1d5a`.
- **Random "dim sign" in the title-B opening scene** (about half of all runs of every build, including the original executable): a shadow surface that flips between depth and colour; cause open (dumps show cube faces at depth 0; clearing does not bring the light back; suspect: a guest CPU read of GPU data at scene start).
- **Text garbling in title B menus**: fixed `7ca6f830d`. In the opening scene a depth read-back refusal ("guest slice larger than image slice") appeared once (default size, before an upstream merge) and did not recur.
- **Upstream merges that cost fps**: `cc817b66` (suspend point released earlier): 20.76 -> 18.98 / 19.21 fps (-7.5%), unmerged in `main` (local merge only; the working tree holds an uncommitted switch). The 2026-11-14 merge `20baba91` was suspected for 38-40 vs 41-44 fps and cleared (pre-merge build already 40): the loss was the fork's own host-view/ownership work and probes (CPU-thread waits 505 -> 597 ms/s). Upstream `704357ab` removed the BDA "accessed tag" the host view needed; upstream's image-heap rework removed the fork's global map and forced run-time learning off. The merge `bd4a9e72` (39 commits) conflicted in five files, was first suspected of a missing character (not reproduced).
- **Tests**: `resource_materialization` failed with upstream's own sources at 41e2147c (disabled, re-enabled after an upstream fix 2026-11-16); several non-CI test modes (ray-tracing size budget, lds-limit, indirect-buffer, scalar-leaf-call, buffer-cache-range) fail identically at `8ebe9a09` (pre-existing); `gpu_command_lane` failed after GPU-ordered labels (test adapted, `KYTY_GPU_SRT=0` in ctest, `5fc608d86`). CI went red on `e5bd71f4` because a macOS runner was unavailable (not code). Compile errors on other toolchains from a serialized field named `S` and an MSVC `std::ranges::find` static assertion (fixed `16a998b53`, again in `fd778fadc`).
- **Crashes seen and fixed**: guest write-back to private runtime mappings (`5cb0e1dfb`); descriptor with base outside guest memory (`ab7bd52e4`); sampler crash in a probe. Seen and not fixed: a quality-mode exit at main-mode load on "invalid buffer discovery request" in title B before the null-bind fix; title C stops at ~35 s with an unhandled guest write to memory it expects mapped (reserve of 512 GB seen, no mapping call follows; not investigated); the title-A compute store through a run-time descriptor needs GPU ownership tracking upstream lacks (the table-store fix covers the title-B case only).
- **Other open items**: quality mode default size is 8.0 fps (4K class; GPU-bound); native RT rewrites only 3 traversal programs and is +3%; guest read faults still wait for whole GPU frames; Nsight attach from the emulator not working; the picture of 720p mode has a larger bloom on one pass (UI/post side stays 4K).
